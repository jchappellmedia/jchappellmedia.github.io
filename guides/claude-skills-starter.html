Claude Skills: the starter pack

A skill is the difference between explaining your process to Claude every single time and never explaining it again. Here's the structure that works, and the mistake that stops most homemade skills from ever running.

What a skill actually is

A skill is a folder. Inside it is a file called SKILL.md, and optionally any scripts, templates or reference documents that file points to. When Claude decides your skill is relevant to the task at hand, it reads SKILL.md and follows it.

That's the whole mechanism. The complexity isn't in the format — it's in getting Claude to choose your skill at the right moment.

The folder structure

my-skill/
├── SKILL.md          ← required; the instructions
├── references/       ← optional; docs Claude reads on demand
│   └── examples.md
└── scripts/          ← optional; things Claude runs
    └── build.py

Keep SKILL.md short. Anything long, rarely needed, or reference-shaped belongs in references/ so it only loads when it's actually wanted.

The frontmatter is the whole ballgame

Every SKILL.md opens with YAML frontmatter:

---
name: invoice-reconciler
description: Reconcile vendor invoices against purchase orders.
  Use when the user mentions invoices, POs, vendor billing,
  reconciliation, or uploads an invoice PDF or spreadsheet.
---

This is where most skills die. The description is the only thing Claude sees when deciding whether to load your skill. If it describes what the skill is but not when to use it, the skill will sit there unused forever.

Write the description in two parts: one sentence on what it does, then an explicit "Use when…" listing the words and situations that should trigger it. Include the vocabulary a real person would actually type — including the sloppy version.

Write the body as instructions, not documentation

Under the frontmatter, write what you'd tell a capable new hire on day one. Imperative, specific, ordered:

  • Steps in order, not a description of the domain.
  • Decision rules for the branches — "if the PO is missing, do X, don't guess."
  • What done looks like, so it knows when to stop.
  • What not to do — the failure modes you've actually hit.

Resist writing background theory. Claude already knows the theory; what it doesn't know is your process.

Five skills worth building first

  1. Your file conventions — where things go in your projects, how you name them.
  2. Your review checklist — whatever you look for before shipping anything.
  3. Your writing voice — with three real before/after examples, which beat any amount of adjectives.
  4. A recurring report — the one you rebuild monthly from the same three sources.
  5. Your intake process — how a new request becomes a scoped piece of work.

Testing whether it fires

Don't ask "use my skill to do X" — that proves nothing. Start a fresh conversation and describe the task the way you naturally would, with no mention of the skill. If it doesn't fire, the description is wrong, not the body. Add the words you just used to the "Use when" line and try again.

A skill that never triggers is worth exactly as much as no skill at all. Spend your time on the description.

Where to go next

Once a skill works, the upgrade path is almost always the same: move the long parts into references/, replace prose instructions with a script where the task is deterministic, and add the edge case you just hit to the "what not to do" list. Skills get good by being corrected, not by being designed.
